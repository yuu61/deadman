# 設定ファイル

設定ファイルは 1 行に 1 項目を書くテキストファイルです。
対象を並べた一覧の順に画面へ表示し、監視します。

- [書式](#書式)
- [宛先](#宛先)
- [監視方式](#監視方式)

- [ディレクティブ](#ディレクティブ)

## 書式

```text
# 名前      アドレス       属性...
local       192.0.2.1
web         example.com    probe=tcp port=443        ;# 行末コメント
--- Web servers
"web 2"     example.net    probe=quic
split 2
```

行は次の 3 種類です。空行は読み飛ばします。

| 行 | 書き方 |
| --- | --- |
| 対象行 | `名前 アドレス [属性...]` |
| 区切り行 | `-` だけでできた語（`---` など）で始める。一覧に区切り線を引き、後ろのコメントを線の中に表示する（`--- Routers / Switches`） |
| ディレクティブ行 | 最初の語が `columns` / `scale` / `precision` / `split` / `glyph`（大文字小文字を区別しない）。[ディレクティブ](#ディレクティブ)を参照 |

- 語はスペースかタブで区切ります。二重引用符で囲んだ部分は空白を含めて 1 つの語になり、引用符は取り除かれます（`key="a b"` のように語の途中でも使えます）。単引用符は普通の文字です。
- `#` で始まる行（字下げしてもよい）はコメントです。引用符の外の `;#`（`;` と `#` の間に空白があってもよい）から行末もコメントです。引用符の中の `#` や `;#` は値の一部です。
- 先頭の UTF-8 BOM は無視します。

区切り行のコメントは空白を含んでも引用符で囲む必要はありません。語の間の空白は 1 つにまとめ、二重引用符の中の空白は保持します。
コメントの左端は HOSTNAME 列の幅の半分の位置に揃え、設定の再読み込みで列幅が変わると追従します。分割表示でも各列内で同じ位置に揃えます。
HOSTNAME 列を隠した場合は、`--- ` の直後から表示します。
区切り行でも `;#` 以降は非表示の行末コメントです。表示するコメントが長い場合は、画面や分割列の幅に収まる部分だけを表示します。

### 対象行の属性

- 属性は `key=value` で書きます。同じ属性を 2 度書くこと、値の空な `key=` は構築エラーです。既定値を使うときは属性ごと省略します。
- 未知の属性、その方式が使わない属性、不正な値、必須属性の欠落も構築エラーです。
- 属性の値は大文字小文字を区別します（`verify=` を除く）。`probe=TCP` や `os=linux` は構築エラーです。
- アドレスの後の `=` を含まない語は無視し、画面上部に警告を出します。空白を含む名前を引用符で囲み忘れた場合などです。閉じていない二重引用符も警告します（行の残りが 1 つの語になります）。

### 構築エラー

構築エラーの行は監視しません。
RESULT 欄に `X` と理由を表示し、統計・履歴・ログに何も加えません。
画面上部の警告は、構築エラーの行の数を 1 行にまとめます。
ほかの行は監視を続けます。設定を直して再読み込み（`R` / SIGHUP）すると、その行の監視を始めます。

## 宛先

アドレスには IP アドレスかホスト名を書きます。画面とログには書いたまま表示します。

- **IP アドレス**: 表記を正規化して扱い、表記の違う同じアドレスは同じ監視経路になります。IPv4-mapped（`::ffff:192.0.2.1`）は IPv4 アドレスとして送ります（中継先の `ping -4` や hping3 が IPv4-mapped の表記を解釈できないため）。ゾーン付きの IPv4-mapped は構築エラーです。
- **ホスト名**: 空白や制御文字を含む名前は、どの方式でも解決できないため構築エラーです。どこで解決するかは方式によります（各方式の説明を参照）。
- 外部コマンドを使う方式（tcp・ssh・netns・vrf）では、コマンドの引数に置く宛先・中継先・名前空間名が `-` で始まると構築エラーです（オプションとして解釈されるため）。

## 監視方式

`probe=` で方式を選びます。省略時は `direct` です。
ほかの属性から方式を推測したり、方式間の優先順位で選んだりはしません。

| `probe=` | 送るもの | 必須の属性 | 任意の属性 |
| --- | --- | --- | --- |
| [`direct`](#direct) | 監視元からの ICMP echo | なし | `source`, `resolve_family` |
| [`nexthop`](#nexthop) | ゲートウェイを強制した ICMP echo（Linux のみ） | `nexthop` | `source` |
| [`tcp`](#tcp) | hping3 による TCP SYN（IPv4 のみ） | `port` | なし |
| [`quic`](#quic) | QUIC ハンドシェイク | なし | `port`, `alpn`, `sni`, `verify`, `resolve_family` |
| [`ssh`](#ssh) | 中継先で実行する ping | `relay`, `os` | `user`, `key`, `source`, `resolve_family` |
| [`netns` / `vrf`](#netns--vrf) | ネットワーク名前空間 / VRF の中で実行する ping（Linux） | `relay` | `source`, `resolve_family` |
| [`routeros`](#routeros) | RouterOS REST API に依頼する ping | `relay`, `username`, `password` | `scheme`, `verify` |
| [`snmp`](#snmp非推奨)（非推奨） | SNMP エージェントに依頼する ping | `relay`, `community` | なし |

```text
local       192.0.2.1
forced      192.0.2.1        probe=nexthop nexthop=192.0.2.254 source=eth0
web         example.com      probe=tcp port=443
h3          example.com      probe=quic
remote      service.internal probe=ssh relay=jump os=Linux resolve_family=ipv4
namespace   service.internal probe=netns relay=ns1 resolve_family=ipv6
router      192.0.2.1        probe=routeros relay=192.0.2.254 username=admin password="secret" verify=off
```

方式ごとの権限・外部コマンド・待ち時間は [動作環境と権限](platform.md) にまとめています。

### direct

監視元から ICMP echo を送ります。
ホスト名は監視元のリゾルバで解決し、返った先頭の 1 アドレスを監視します。特定の 1 台を続けて監視したい場合は IP アドレスを書いてください。
解決するファミリーは `resolve_family` か送信元アドレスで固定できます。
`source=` にインタフェース名を書くと、そのインタフェースから送り、送信元アドレスは宛先に合わせてカーネルが選びます。

### nexthop

指定したゲートウェイ（`nexthop=`）の MAC アドレスへ直接 ICMP echo を送り、特定の経路での到達性を監視します。
Linux 専用で、ほかの OS では構築エラーです。root か `CAP_NET_RAW` が必要です。

- `nexthop=` は on-link の IP アドレスで、ゾーン表記は使えません。IPv4-mapped は IPv4 に正規化します。
- 宛先の IP アドレスはゲートウェイと同じファミリーが必要です。宛先のホスト名はゲートウェイのファミリーで解決します。宛先にゾーン表記は使えません（出口はゲートウェイと `source=` で決まるため）。
- `source=` には出口のインタフェース名か、ゲートウェイと同じファミリーの送信元アドレス（ゾーン表記なし）を書きます。リンクローカル（`fe80::/10`）のゲートウェイでは、インタフェース名が必須です。
- IPv6 の送信元は、宛先と同じ種類（ULA / GUA）のアドレスを優先し、無ければ使えるグローバルスコープのアドレスを使います。リンクローカルの宛先にはリンクローカルの送信元が必要です。
- ゲートウェイが ARP / NDP に応答しない場合は、強制した経路が最初のホップで途絶えているので、無応答（`X`、損失）として数えます。

### tcp

hping3 で `port=` に TCP SYN を送り、応答を確かめます。
`port=` は必須で、1〜65535 の整数です。
hping3 は IPv4 専用のため、宛先に IPv6 アドレスを書くと構築エラーです。ホスト名は hping3 が IPv4 で解決します。

### quic

QUIC ハンドシェイクが完了するまでの時間を RTT として測ります。外部コマンドや特権は要りません。

| 属性 | 既定値 | 説明 |
| --- | --- | --- |
| `port=` | `443` | 1〜65535 |
| `alpn=` | `h3` | ALPN。255 バイト以内 |
| `sni=` | 宛先のホスト名（IP アドレスなら無し） | TLS の ServerName。IP アドレスで HTTP/3 を監視するときは、必要に応じて指定する |
| `verify=` | `off` | 証明書を検証するか |
| `resolve_family=` | なし | [共通の属性](#resolve_family) |

ホスト名は direct と同じく監視元で解決します。
ハンドシェイクの時間切れは無応答（`X`）です。ソケットを作れない、TLS の検証に失敗した、プロトコルエラーになった場合は、対象を観測できなかった（`?`）として扱います。

### ssh

`relay=` のホストへ ssh で入り、そこで ping を実行します。

- `relay=HOST` か `relay=USER@HOST` で書きます。`relay=ops@jump` は `relay=jump user=ops` と同じで、両方にユーザーを書いた場合は `relay=` 内のユーザーを使います。ユーザーやホストが空のもの、`@` が 2 つ以上あるもの、空白や制御文字を含むものは構築エラーです。
- `os=Linux|Darwin|FreeBSD` は必須です。中継先の ping の書式を決めるもので、監視元の OS から推測しません。
  - Linux と FreeBSD は IPv6 を `ping -6` で送り、ホスト名を IPv4 で送るときは `ping -4` を付けます（FreeBSD は `-4` / `-6` を持つ 13 以降が必要）。
  - Darwin の IPv6 は `ping6` で送ります。応答が無いと約 10 秒待ちます（[待ち時間](platform.md#プローブの待ち時間)）。
- `user=` はログインユーザー、`key=` は秘密鍵のファイル（`ssh -i`）です。
- ssh は `BatchMode=yes` で動かすため、パスワードや鍵のパスフレーズを尋ねません。鍵認証を用意し、パスフレーズ付きの鍵は ssh-agent に載せてください。尋ねる必要のある中継は `s` になります。
- 中継のホスト鍵は、初回の接続で known_hosts に登録します（`StrictHostKeyChecking=accept-new`）。登録済みの鍵が変わった中継は拒否し、`s` になります。
- ping の引数は中継先のシェル向けに引用して渡すため、宛先名や送信元の空白・ワイルドカード・`$(...)` は展開されません。
- `source=` は、Linux ではアドレスとインタフェース名、Darwin ではアドレスだけ使えます。FreeBSD では指定できません。
- 宛先がホスト名なら、`resolve_family` か送信元アドレスが必須です。名前は中継先で解決します。

### netns / vrf

監視元の Linux で `ip netns exec NAME` / `ip vrf exec NAME` を通して ping を実行します。
`relay=` に名前空間名 / VRF 名を書きます。
ping の書式は Linux に決まるため、`os=` は書けません。
`source=` はアドレスとインタフェース名のどちらも使えます。
宛先がホスト名なら、`resolve_family` か送信元アドレスが必須です。名前は名前空間 / VRF の中で解決します。

### routeros

RouterOS の REST API に ping を依頼します。外部コマンドは使いません。

- `relay=` には API のホスト名か IP アドレスを書き、TCP ポートを付けられます。例: `relay=router.example:8443`、`relay=[2001:db8::1]:8443`、ゾーン付きは `relay=[fe80::1%ether1]:8443`。
- ホスト名は英数字・`-`・`_`・`.` で書きます。URL、認証情報、パス、それ以外の文字、ホストの無い `:8443`、無効なポートは構築エラーです。
- `scheme=http|https` は API の通信方式で、既定は `https` です。ポートを省略すると、https は 443、http は 80 を使います。
- IP アドレスの表記の違い、ポートの先行ゼロ、方式の既定ポートの明示は、同じ監視経路として扱います。ホスト名は書いたまま扱います。
- `username=` と `password=` は必須です。
- `verify=` は証明書を検証するかで、既定は `on` です。
- API に届かない・拒否された・ping の結果以外を返した場合は、中継の失敗として表示し（時間切れは `t`、それ以外は `s`）、統計に加えません。

### snmp（非推奨）

SNMPv2c でエージェントに RFC 4560（DISMAN-PING-MIB）の ping を依頼します。
この MIB を実装したエージェントは少なく、実機での動作は確認できていないため、非推奨です。
今の設定は引き続き動きますが、起動時と再読み込み時に、この方式の対象名を並べて警告します。

- `relay=` はエージェントのホスト名（英数字・`-`・`_`・`.`）か IP アドレスで、UDP 161 番に送ります。Net-SNMP のトランスポート指定（`udp6:[::1]:161`）やポート付きの `host:1161` は構築エラーです。
- `community=` はコミュニティ名です。
- 宛先のホスト名は監視元で解決し（先頭の 1 アドレス。ファミリーは選べません）、アドレスだけをエージェントに渡します。宛先・エージェントとも IPv6 アドレスを使えますが、宛先のゾーン表記はエージェントに伝わらないため構築エラーです。
- プローブごとに pingCtlTable の行を作り、結果を読み、行を削除します。`pingCtlType` には `pingIcmpEcho` を明示します（MIB の既定値ですが、H3C・Huawei は明示を求めます）。
- エージェントは、1 つの PDU での行の作成と開始（`createAndGo`）と、InetAddress 形式の宛先（IPv4 は 4 オクテット、IPv6 は 16 オクテット）を受け付ける必要があります。
- 公開資料で実装が確認できるのは Juniper・H3C・Huawei・Allied Telesis などです（Juniper は IPv6 に非対応）。Cisco IOS XE・Yamaha RTX・FortiOS は実装していません。Net-SNMP の `snmpd` は既定で実装しておらず、オプションの実装（5.9.4 で確認）もこの要求を受け付けません。
- エージェントが要求を拒否したとき（MIB を実装していないときを含む）は `s`、応答しないときは `t` です。エージェントが送ったプローブに応答が無かったときだけ `X` になります。RTT はエージェントが測った値で、ミリ秒単位の整数です。

## 共通の属性

### source

プローブの送信元です。`direct` / `nexthop` / `ssh` / `netns` / `vrf` で使え、ほかの方式に書くと構築エラーです。

- IP アドレスとして読める値は送信元アドレス、それ以外はインタフェース名です。アドレスにはゾーン付き（`fe80::1%eth0`）も書けます。IPv4-mapped は IPv4 に正規化し、ゾーン付きの IPv4-mapped は構築エラーです。
- 送信元アドレスは、送信するファミリー（宛先の IP アドレス、`resolve_family`、nexthop のゲートウェイ）と同じでなければ構築エラーです。食い違う送信元はどの経路でも使えず、別の送信元から送られるか、失敗し続けるためです。
- 宛先がホスト名なら、送信元アドレスのファミリーで解決します。
- 方式ごとの制限は [nexthop](#nexthop) と [ssh](#ssh) を参照してください。

### resolve_family

`resolve_family=ipv4|ipv6` は、ホスト名の宛先を送るファミリーを固定します。
画面の ADDRESS 列には `google.com [IPv4]` / `google.com [IPv6]` のように表示し、同じホスト名の監視を見分けられます。

- `direct` / `quic` では、監視元で解決するレコードを選びます。
- `ssh` / `netns` / `vrf` では、中継先で実行する ping のファミリー（`-4` / `-6`）を選びます。監視元の DNS には問い合わせず、名前解決は ping を実行する側に任せます。宛先がホスト名なら、これか送信元アドレスが必須です。
- 宛先が IP アドレスなら省略でき、書いたファミリーがアドレスと異なると構築エラーです。
- 省略すると、送信元アドレスを書いた行ではそのファミリーになります。

### verify

`verify=on|off` は TLS 証明書を検証するかです。`quic` と `routeros` で使えます。
`true` / `false`、`yes` / `no`、`1` / `0` も、大文字小文字を区別せずに受け付けます。
既定は `quic` が `off`、`routeros` が `on` です。

## ディレクティブ

ディレクティブ行は、表示の起動時の値を決めます。

```text
split     2
columns   ADDRESS=off MIN=off MAX=off
scale     5
precision ms.1
glyph     digit
```

| ディレクティブ | 値 | 既定 | 対応するオプション / キー |
| --- | --- | --- | --- |
| `split N` | 段組みの列数（正の整数） | `1` | `-c` / `[` `]` |
| `columns KEY=on\|off ...` | 列ごとの表示 | すべて表示 | `m` `v` `h` `a` |
| `scale N` | RESULT バーの 1 段あたりの幅（ms、0.0001〜1000000、小数可） | `1` | `-s` / `↑` `↓` |
| `precision MODE` | 統計の表示精度（`ms` / `ms.1` / `ms.2` / `ms.3`） | `ms` | `p` |
| `glyph MODE` | RESULT バーの文字（`auto` / `block` / `ascii` / `digit`） | `auto` | `-g` / `b` |

- ディレクティブ名と値（列名、`precision` / `glyph` の名前、on / off）は大文字小文字を区別しません。
- 同じディレクティブが複数行ある場合は、書式として正しい最後の行が有効です。`scale` / `split` に数値でない値を書いた行は無視します。
- 使えない値（範囲外の `scale`、正でない `split`、未知の `precision` / `glyph` の名前）は捨て、既定値を使います。
- オプションはディレクティブより優先されます。使えない `-s` / `-c` の値は画面上部に警告を出して無視し、ディレクティブか既定値を使います。`-g` の未知の値は起動時のエラーです。
- 再読み込み（`R` / SIGHUP）で反映するのは `columns` だけです。ほかのディレクティブは、キーで変えたかもしれない実行中の値を保ちます。

### split

一覧を指定した列数に折り返して表示します。列を増やすと RESULT バーは短くなります。
端末の幅に収まらない列数は、収まるまで減らして表示します。

### columns

`KEY=on|off` を空白で区切って並べます。`on` / `off` のほか `true` / `false`、`yes` / `no`、`1` / `0` も使えます。
`KEY` は次のとおりです。未知のキーや値は無視します。RESULT 列は隠せません。

`HOSTNAME` `ADDRESS` `VIA` `LOSS` `RTT` `AVG` `MIN` `MAX` `JIT` `SNT` `FAIL`

各列の意味は [画面の見方](display.md#列) を参照してください。

### scale / precision / glyph

- `scale` は、RESULT バーの 1 段が受け持つ RTT の幅です（対数表示では最も低い段の上限）。段の決まり方は [RESULT バー](display.md#result-バー) を参照してください。
- `precision` は、RTT / AVG / MIN / MAX / JIT 列の小数点以下の桁数です（`ms.N` で N 桁）。桁を増やすほどサブミリ秒の差が見えます。
- `glyph` は、応答したプローブを描く文字の組です。`auto` は端末を判定して `block` か `ascii` を選びます（[文字の組](display.md#文字の組)）。

## 行の同一性

各行は、監視経路と、同じ監視経路の行の中での出現順で見分けます。これを行の同一性と呼びます。

- 再読み込みでは、同一性の同じ行が統計と履歴を引き継ぎます。
- `-l` のログのファイル名は同一性から作ります（[ログ](logging.md)）。
- 同じ監視経路の行が複数あれば、出現順で別の行として扱い、統計・履歴・ログファイルを分けます。

監視経路は、方式、正規化した宛先、次の表の条件でできています。
条件は既定値を埋めた後の値で比べるため、既定値を書いても省略しても同じ監視経路です。
宛先の IP アドレスや送信元アドレスから決まるファミリーも、`resolve_family` を書いたかどうかでは変わりません。

| `probe=` | 監視経路に入る条件 | 入らない属性 |
| --- | --- | --- |
| `direct` | `source`, `resolve_family` | |
| `nexthop` | `nexthop`, `source` | |
| `tcp` | `port` | |
| `quic` | `port`, `alpn`, `sni`, `verify`, `resolve_family` | |
| `ssh` | `relay` のホスト, `os`, `source`, `resolve_family` | `user`（`relay=` 内のユーザーを含む）, `key` |
| `netns` / `vrf` | `relay`, `source`, `resolve_family` | |
| `routeros` | `relay` のホストとポート, `scheme`, `verify` | `username`, `password` |
| `snmp` | `relay` | `community` |

- 名前、認証情報（`user` / `key` / `username` / `password` / `community`）を変えても、同じ行のままです。
- 条件を変えると、新しい履歴と新しいログファイルで始まります。`verify` の切り替えは成功とみなす条件が変わるため、ここに含めています。
- 出現順は構築できた行だけで数えます。同じ監視経路の行が複数あるときに前の行を構築エラーにすると、後の行が繰り上がって、その行の履歴とログファイルを引き継ぎます。

## 旧版からの移行

旧構文の互換処理はありません。次の表に従って書き換えてください。

| 旧設定 | 新設定 |
| --- | --- |
| `via=quic` | `probe=quic` |
| `via=snmp relay=... community=...` | `probe=snmp relay=... community=...` |
| `via=netns relay=...` / `via=vrf relay=...` | `probe=netns relay=...` / `probe=vrf relay=...` |
| `relay=jump` | `probe=ssh relay=jump os=Linux`（実際の中継先の OS を書く） |
| `tcp=dstport:80` | `probe=tcp port=80` |
| `via=routeros_api method=https ...` | `probe=routeros scheme=https ...` |
| `nexthop=192.0.2.254` | `probe=nexthop nexthop=192.0.2.254` |

- 複数の方式の属性を混ぜて書いていた行は、使う方式の属性だけを残します。使われずに無視されていた属性も削除します。
- 値の空な `key=` を書いていた行は、属性ごと削除します。
- ssh / netns / vrf の宛先がホスト名なら、`resolve_family` を追加します。
- ログのファイル名の付け方も変わりました（[ログ](logging.md#旧版からの移行)）。
